# Todolist, goal и под-агенты

Дата: 10.11.2026
Статус: утверждён (решения пользователя получены 10.11.2026)

## 1. Контекст

Панель агента умеет читать и писать файлы, искать по проекту, запускать команды и git.
Чего ей не хватает:

1. Списка задач. Модель ведёт дела, но пользователь не видит план и не видит прогресс.
2. Цели с бюджетом. Длинная задача крутится, пока не упрётся в лимит итераций.
   Пользователь не может сказать "стоп, потрачено слишком".
3. Под-агентов. Сложная задача решается одним контекстом, модель пытается сделать
   всё сама и упирается в окно.

Три механизма вводятся по очереди: сначала todolist, потом goal, потом агенты.
Каждый даёт пользователю новый рычаг над ходом агента.

## 2. Решения пользователя

| Вопрос | Решение |
|---|---|
| Что такое goal | Цель с лимитами и автостопом по бюджету |
| Что такое агенты | Под-агенты через инструмент `task` |
| Где живёт todolist | Виджет над чатом |
| Порядок работ | Сначала todolist, потом goal, потом агенты |

## 3. Общий каркас

Состояние живёт в хосте, модель меняет его через инструменты, панель получает снимок.

Три правила:

1. **Хост единственный владелец состояния.** Инструмент не меняет состояние сессии сам.
   Он возвращает снимок в результате вызова, хост применяет снимок и отправляет его в панель.
2. **Снимок, а не дельта.** `todo_write` присылает весь список, хост заменяет список
   целиком. Разбор дельт не нужен и не будет добавлен.
3. **Состояние переживает перезагрузку окна.** Список задач и цель лежат в сохранённой сессии.

Путь данных:

```
модель -> инструмент -> ToolExecutionResult.state -> AgentEvent tool_end
       -> хост -> RuntimeSession -> {type:'todos'} / {type:'goal'} -> панель
```

Новый модуль `src/agent/state.ts` с типами:

```ts
export type TodoStatus = 'pending' | 'in_progress' | 'completed';
export type TodoPriority = 'high' | 'medium' | 'low';

export interface TodoItem {
  content: string;
  status: TodoStatus;
  priority: TodoPriority;
}

export type GoalStatus = 'active' | 'complete' | 'blocked';

export interface GoalState {
  objective: string;
  tokenBudget?: number;
  requestLimit?: number;
  secondsLimit?: number;
  status: GoalStatus;
  used: { tokens: number; requests: number; seconds: number };
}
```

Снимок состояния, который возвращает инструмент:

```ts
export type ToolStateUpdate =
  | { kind: 'todos'; todos: TodoItem[] }
  | { kind: 'goal'; status: 'complete' | 'blocked'; note?: string };
```

`ToolExecutionResult` получает поле `state?: ToolStateUpdate`, событие `tool_end`
агента тоже.

Инструменту нужен id его вызова: `ToolContext.callId`. По нему журнал ребёнка
попадает в карточку того вызова `task`, который его запустил. Рядом с ним
`ToolContext.depth`: 0 у родителя, 1 у ребёнка.

## 4. Todolist

### 4.1 Инструмент

`todo_write(todos)`:

- `todos`: массив `{ content, status, priority }`, `content` обязателен,
  `status` и `priority` необязательны.
- `approval: 'never'`, `sideEffect: false`, доступен в режимах plan и code.
- Недоступен под-агенту: `ctx.depth > 0` даёт отказ
  "The list of tasks belongs to the main agent."

Нормализация делается в инструменте, до снимка: запись с пустым `content` отбрасывается,
неизвестный `status` становится `pending`, неизвестный `priority` становится `medium`.
Пустой массив очищает список.

### 4.2 Хост

`RuntimeSession.todos: TodoItem[]`, `StoredSession.todos?: TodoItem[]`.

Хост на `tool_end` со снимком `{kind:'todos'}`:

1. Кладёт список в `runtime.todos`.
2. Шлёт `{type:'todos', todos}` в панель.
3. Сохраняет сессию.

### 4.3 Промпт

Раздел `Tasks:` рядом с `Repository:` в контексте перед каждым ходом.
Формат строки: `- [in_progress] Rewrite the parser (high)`.
Раздел отсутствует, когда список пуст.

Разделы контекста собирает хост в том же провайдере, что и `Repository:`.
Рендер живёт в `src/agent/prompt.ts` рядом с `renderGitContext`:
`renderTasksContext(todos)` и `renderGoalContext(goal)`.

### 4.4 Панель

Виджет `Tasks` над лентой чата:

- Шапка `Tasks 2/5`: два выполнено из пяти. Клик по шапке сворачивает и разворачивает
  список, состояние живёт в панели.
- Строки: слева маркер состояния, текст задачи, справа метка приоритета.
  `high` в акцентном цвете, `medium` и `low` приглушены.
- Клик по строке ничего не делает: список ведёт модель, а не пользователь.
  Это осознанное решение, иначе панель и модель начинают спорить за состояние.
- Виджет появляется, когда список не пуст, и исчезает, когда список очищен.

## 5. Goal

### 5.1 Состояние

`RuntimeSession.goal: GoalState | undefined`. Цель ставит пользователь, снимает пользователь,
статус меняет модель.

### 5.2 Виджет и форма

Виджет `Goal` над лентой чата, под виджетом `Tasks`:

- Строка цели: текст objectives, справа расход: `12.3k / 50k tokens`,
  `3 / 10 requests`, `1m 20s / 5m`. Лимита, которого нет, показывается как `∞`.
- Кнопка `Edit` открывает форму: objective (обязательное поле), лимит токенов,
  лимит запросов, лимит минут. Пустое поле означает "без лимита".
  Кнопка `Clear` снимает цель.
- Статус `complete` и `blocked` показывается меткой в шапке виджета.

Форма шлёт `set_goal` с objective и лимитами или `clear_goal`.

### 5.3 Инструменты

- `get_goal()`: возвращает текстом цель, лимиты и расход.
  `approval: 'never'`, `sideEffect: false`.
- `update_goal(status, note?)`: `status` это `complete` или `blocked`,
  `note` необязателен и короткий. Возвращает снимок `{kind:'goal', status, note}`,
  хост применяет его.

**Решение: модель не может менять лимиты.** Иначе автостоп обходится самой моделью,
и лимит перестаёт быть ограничением. Лимит поднимает пользователь в форме виджета,
после чего агент продолжает работу следующим запросом.

### 5.4 Расход и автостоп

Сейчас хост узнаёт расход только в конце хода (событие `done`),
а лимит обязан срабатывать в середине. Поэтому:

- Новое событие агента `{ type: 'usage'; usage: Usage }`: дельта расхода одного запроса
  к API. Агент шлёт его после каждого стрима.
- Хост накапливает: `used.tokens += input + output + cache`, `used.requests += 1`.
- Время: `used.seconds` копит длительность ходов, прошедших под целью.
  Проверка идёт по времени текущего хода, чтобы остановить его посередине.

Проверка бюджета в хосте, после каждого запроса:

- токены: `used.tokens >= tokenBudget`;
- запросы: `used.requests >= requestLimit`;
- время: `used.seconds + длительность текущего хода >= secondsLimit`.

Любое из условий срабатывает: агент останавливается, статус цели остаётся `active`,
в панель уходят заметка и снимок цели. Пользователь поднимает лимит и продолжает.

Механизм остановки: у агента появляется опция `budget?: () => boolean` ("можно продолжать").
Агент зовёт её после каждого запроса и, если ответ отрицательный, заканчивает цикл
с новой причиной остановки `goal_limit`.

`StopReason` получает значение `goal_limit`. `stopNotice` даёт для него заметку
"The budget of the goal is exhausted, the agent stopped. Raise the limit and send the next
request." с типом `warn`.

Проверка идёт до выполнения инструментов: когда бюджет исчерпан, модель не получает
ещё один круг работы.

### 5.5 Промпт

Раздел `Goal:` в контексте перед каждым ходом: цель, лимиты и расход.

```
Goal: Rewrite the parser
Budget: 12000 tokens, 10 requests, 300 seconds
Used: 4300 tokens, 2 requests, 65 seconds
```

Раздел отсутствует, когда цели нет. Рендер: `renderGoalContext(goal)`
в `src/agent/prompt.ts`.

## 6. Под-агенты

### 6.1 Инструмент

`task(description, prompt, role?)`:

- `description`: короткое имя задачи, одна строка, попадает в заголовок карточки.
- `prompt`: задание для ребёнка, основной текст.
- `role`: `explore` (по умолчанию), `worker` или `verifier`.

Инструмент сам побочных эффектов не имеет, но внутри запускает агента, который может
писать файлы, поэтому `sideEffect: true`: в режиме plan инструмент недоступен.

`approval: 'never'`: подтверждения запрашивает сам ребёнок, когда его инструмент
меняет проект.

### 6.2 Роли

| Роль | Инструменты | Что делает |
|---|---|---|
| `explore` | только чтение (`sideEffect === false`) | ищет и читает код |
| `worker` | все | правит файлы и запускает команды |
| `verifier` | только чтение | проверяет чужую работу |

Роль по умолчанию `explore`: роль без записи безопаснее, а модель обязана назвать
`worker` явно, если нужны правки.

### 6.3 Ребёнок

- Своя история с нуля: одно сообщение пользователя с текстом `prompt`.
- Свой системный промпт: промпт родителя плюс абзац роли ("ты ищешь и читаешь код
  и отвечаешь текстом" или "ты вносишь правки и отвечаешь текстом") и требование
  вернуть итог текстом.
- Свой реестр инструментов: новый `ToolRegistry`, в который попадают записи родителя,
  разрешённые ролью. Режим агента (plan или code) действует и на ребёнка.
- Тот же гейт подтверждений: запись файла ребёнком спрашивает пользователя.
  Запрос на подтверждение ребёнка получает id с префиксом `child-`, чтобы не спутать
  его с запросом родителя.
- Своя итерация: не больше `CHILD_MAX_ITERATIONS = 12`.
- Глубина: `ToolContext.depth` равен 0 у родителя и 1 у ребёнка.
  Инструмент `task` при `depth > 0` отказывает:
  "A sub-agent cannot start another sub-agent."

### 6.4 Поток событий

События ребёнка не идут в ленту отдельными карточками, они собираются в карточке `task`:

- `tool_start` и `tool_end` ребёнка дают строку журнала
  (`read_file src/app.ts`, `search_code "parser" 3 matches`).
- Текст ребёнка даёт строку журнала с усечённым текстом.
- Итоговый ответ ребёнка это результат вызова `task`, его видит родительская модель
  и пользователь в карточке.

Новое сообщение протокола `tool_progress`: `{ type: 'tool_progress'; id: string; line: string }`,
где `id` это id вызова `task` в панели.

Карточка `task`: заголовок `Task <description>`, тело это журнал и ответ.
Ответ рендерится markdown через существующий `renderMarkdown`, тот же рендерер,
что и у ответов агента.

### 6.5 Расход

Токены ребёнка идут в счёт сессии и в график расхода. Результат вызова `task` несёт
`usage` ребёнка, агент родителя прибавляет его к расходу своего хода, поэтому
у действия `task` одна колонка в графике с суммой.

Расход ребёнка по цели считается отдельно: событие `usage` ребёнка доходит до хоста
и попадает в тот же счётчик, что и расход родителя. Иначе ребёнок обходил бы лимит цели.

### 6.6 Где живёт реализация

Хост создаёт ребёнка, инструмент только просит: `createTaskTools({ spawn })`,
где `spawn` это функция хоста. В инструменте нет ни ключа, ни клиента, ни реестра.

Хост в `spawn`:

1. Берёт ключ из секретов и настройки.
2. Собирает реестр по роли.
3. Создаёт `Agent` с `depth: 1` и гардом бюджета.
4. События ребёнка перенаправляет: `usage` в общий счёт, остальные в `tool_progress`
   панели.
5. Возвращает итоговый текст и расход.

## 7. Протокол

`ExtToWeb` получает:

- `{ type: 'todos'; todos: TodoItem[] }`
- `{ type: 'goal'; goal?: GoalState }`
- `{ type: 'tool_progress'; id: string; line: string }`

`WebToExt` получает:

- `{ type: 'set_goal'; objective: string; tokenBudget?: number; requestLimit?: number; secondsLimit?: number }`
- `{ type: 'clear_goal' }`

`UiState` получает `todos: TodoItem[]` и `goal?: GoalState`, чтобы состояние
пришло при перезагрузке окна.

## 10. Вне области

- Настраиваемые пользователем профили агентов и свободные роли: роли заданы кодом.
- Параллельные под-агенты: цикл агента выполняет вызовы последовательно.
- Отдельная вкладка для задач и цели: виджеты стоят над лентой.
- Экспорт списка задач.
- Модель не меняет лимиты цели.
- Список задач ведёт только корневой агент.
